## 1. Overview

### 1.1 Purpose

This runbook provides step-by-step procedures for on-call engineers responding to Robot Shop production incidents. It is designed to minimize Mean Time to Resolution (MTTR) by providing clear, actionable diagnosis and mitigation steps for each alert.

### 1.2 Scope

This runbook covers alerts generated by the Prometheus/Alertmanager stack monitoring the Robot Shop application deployed in the `robot-shop` Kubernetes namespace on Amazon EKS.

### 1.3 On-Call Rotation

- **Primary On-Call:** Receives PagerDuty page for all P1/P2 alerts
- **Secondary On-Call:** Backup if primary is unresponsive after 10 minutes
- **Engineering Lead:** Escalation for P1 incidents > 30 minutes unresolved
- **Rotation:** Weekly, Monday 09:00 UTC handoff
- **Schedule:** PagerDuty schedule `robot-shop-oncall`

### 1.4 Before You Start

When paged, always do these steps first:

1. **Acknowledge** the PagerDuty alert within 5 minutes
2. **Post** to `#sre-incidents`: `🔍 Investigating [ALERT_NAME] — @<your_handle> on it`
3. **Open** the Grafana dashboard: `http://grafana.monitoring.svc/d/robot-shop-overview`
4. **Check** if there's an ongoing incident already being handled
5. **Review** recent deployments in `#deployments` Slack channel

### 3.1 RobotShopWebHighErrorRate

**Alert Expression:**
```promql
sum(rate(http_requests_total{service="web", code=~"5.."}[5m]))
  / sum(rate(http_requests_total{service="web"}[5m])) > 0.01
```

**Firing Condition:** HTTP 5xx error rate > 1% over a 5-minute window  
**Severity:** Critical  
**SLO Impact:** Directly burns error budget

#### Symptoms
- Users reporting errors on the Robot Shop website
- Grafana shows spike in 5xx error rate on the "Web Service" panel
- Possible customer complaints via support channels

#### Diagnosis Steps

**Step 1: Check web pod health**
```bash
# List web pods and their status
kubectl get pods -n robot-shop -l service=web

# Check events for anomalies
kubectl get events -n robot-shop --sort-by='.lastTimestamp' | tail -20
```

**Step 2: Examine web pod logs**
```bash
# Stream last 100 lines of web pod logs
kubectl logs -n robot-shop -l service=web --tail=100

# Follow logs in real-time
kubectl logs -n robot-shop -l service=web -f

# Look for error patterns
kubectl logs -n robot-shop -l service=web --tail=500 | grep -E "ERROR|FATAL|5[0-9]{2}"
```

**Step 3: Check Redis connectivity** (web service depends on Redis for sessions)
```bash
# Check Redis pod status
kubectl get pods -n robot-shop -l service=redis

# Check Redis logs
kubectl logs -n robot-shop -l service=redis --tail=50

# Test Redis connectivity from web pod
kubectl exec -n robot-shop -it $(kubectl get pod -n robot-shop -l service=web -o jsonpath='{.items[0].metadata.name}') \
  -- redis-cli -h redis ping
```

**Step 4: Check catalogue service** (web calls catalogue for product data)
```bash
# Catalogue pod status
kubectl get pods -n robot-shop -l service=catalogue

# Catalogue logs
kubectl logs -n robot-shop -l service=catalogue --tail=100

# Check catalogue service endpoint
kubectl get endpoints -n robot-shop catalogue
```

**Step 5: Check Ingress / Load Balancer**
```bash
# Check ingress status
kubectl get ingress -n robot-shop

# Check ingress controller logs
kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx --tail=50
```

#### Mitigation

**Option A: Rollback recent deployment** (if error started after deploy)
```bash
# Check deployment history
kubectl rollout history deployment/web -n robot-shop

# Rollback to previous revision
kubectl rollout undo deployment/web -n robot-shop

# Monitor rollout
kubectl rollout status deployment/web -n robot-shop
```

**Option B: Scale up web deployment** (if resource exhaustion is suspected)
```bash
# Scale web replicas
kubectl scale deployment web -n robot-shop --replicas=5

# Verify
kubectl get pods -n robot-shop -l service=web
```

**Option C: Restart pods** (if individual pods are wedged)
```bash
# Delete and recreate pods (deployment will restart them)
kubectl delete pods -n robot-shop -l service=web
```

#### Escalation
- Escalate to **Engineering Lead** if error rate > 10% and persists > 10 minutes
- Escalate to **VP Engineering** if error rate > 50% (full outage scenario)
- Open P1 incident if users are broadly impacted

### 3.2 RobotShopHighLatency

**Alert Expression:**
```promql
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket{namespace="robot-shop"}[5m])) by (le, service)
) > 0.5
```

**Firing Condition:** P99 latency > 500ms across any Robot Shop service  
**Severity:** Warning (escalates to Critical if > 2s)

#### Symptoms
- Users report slow page loads
- Grafana latency panels show elevated P99
- Cart or checkout operations timing out

#### Diagnosis Steps

**Step 1: Identify the slowest service**
```bash
# Check resource utilization across all pods
kubectl top pods -n robot-shop

# Sort by CPU
kubectl top pods -n robot-shop --sort-by=cpu
```

**Step 2: Check database connections** (slow DB queries are a common cause)
```bash
# Check MongoDB pod (catalogue uses MongoDB)
kubectl get pods -n robot-shop -l service=mongodb
kubectl logs -n robot-shop -l service=mongodb --tail=100

# Check MySQL pod (payment uses MySQL)
kubectl get pods -n robot-shop -l service=mysql
kubectl logs -n robot-shop -l service=mysql --tail=100 | grep -i "slow\|error\|connection"
```

**Step 3: Check pod resource limits**
```bash
# Describe web deployment to see resource requests/limits
kubectl describe deployment web -n robot-shop | grep -A 10 "Limits\|Requests"

# Check if pods are being CPU throttled
kubectl top pods -n robot-shop
```

**Step 4: Check Horizontal Pod Autoscaler (HPA) status**
```bash
# List all HPAs
kubectl get hpa -n robot-shop

# Check HPA details (is it scaling?)
kubectl describe hpa -n robot-shop
```

**Step 5: Check Jaeger traces** for distributed tracing  
Navigate to: `http://jaeger.monitoring.svc/search?service=web&limit=20`  
Look for traces with duration > 500ms to pinpoint the bottleneck.

#### Mitigation

**Option A: Temporarily increase replicas**
```bash
kubectl scale deployment web -n robot-shop --replicas=6
kubectl scale deployment catalogue -n robot-shop --replicas=4
```

**Option B: Adjust resource limits** (if throttling)
```bash
kubectl set resources deployment web -n robot-shop \
  --limits=cpu=500m,memory=512Mi \
  --requests=cpu=250m,memory=256Mi
```

**Option C: Investigate and restart slow pod**
```bash
# Identify oldest/slowest pod
kubectl get pods -n robot-shop -o wide
kubectl delete pod <slow-pod-name> -n robot-shop
```

#### Escalation
- Escalate to **Database Admin** if MySQL or MongoDB slow queries are detected
- Escalate to **Engineering Lead** if latency > 2s and persists > 15 minutes

### 3.3 RobotShopCartPaymentDown

**Alert Expression:**
```promql
up{namespace="robot-shop", service=~"cart|payment"} == 0
# OR
sum(rate(http_requests_total{namespace="robot-shop", service=~"cart|payment", code=~"5.."}[5m]))
  / sum(rate(http_requests_total{namespace="robot-shop", service=~"cart|payment"}[5m])) > 0.05
```

**Firing Condition:** Cart or Payment service unavailable or > 5% error rate  
**Severity:** Critical (direct revenue impact)

#### Symptoms
- Customers cannot add items to cart or complete checkout
- Payment failures on the checkout page
- Grafana shows cart/payment services as DOWN (red)

#### Diagnosis Steps

**Step 1: Check payment pod status and logs**
```bash
# Check payment pods
kubectl get pods -n robot-shop -l service=payment -o wide

# Describe a payment pod for events
kubectl describe pod -n robot-shop -l service=payment

# Check payment logs for errors
kubectl logs -n robot-shop -l service=payment --tail=200
kubectl logs -n robot-shop -l service=payment --tail=200 | grep -iE "error|fail|exception|mysql|rabbitmq"
```

**Step 2: Check MySQL connectivity** (payment service requires MySQL)
```bash
# MySQL pod status
kubectl get pods -n robot-shop -l service=mysql

# MySQL logs
kubectl logs -n robot-shop -l service=mysql --tail=100

# Test MySQL connectivity from payment pod
kubectl exec -n robot-shop -it \
  $(kubectl get pod -n robot-shop -l service=payment -o jsonpath='{.items[0].metadata.name}') \
  -- mysql -h mysql -u <DB_USER> -p<DB_PASS> -e "SELECT 1;"
```

**Step 3: Check RabbitMQ** (payment uses RabbitMQ for async order processing)
```bash
# RabbitMQ pod status
kubectl get pods -n robot-shop -l service=rabbitmq

# RabbitMQ logs
kubectl logs -n robot-shop -l service=rabbitmq --tail=100

# Check RabbitMQ management UI (port-forward)
kubectl port-forward -n robot-shop svc/rabbitmq 15672:15672
# Open http://localhost:15672 (guest/guest) — check queue depths
```

**Step 4: Check cart service and Redis**
```bash
# Cart pod status
kubectl get pods -n robot-shop -l service=cart

# Cart logs
kubectl logs -n robot-shop -l service=cart --tail=200

# Redis health
kubectl exec -n robot-shop -it \
  $(kubectl get pod -n robot-shop -l service=redis -o jsonpath='{.items[0].metadata.name}') \
  -- redis-cli info stats | grep -E "instantaneous|rejected"
```

#### Mitigation

**Option A: Restart payment/cart pods**
```bash
kubectl rollout restart deployment/payment -n robot-shop
kubectl rollout restart deployment/cart -n robot-shop
kubectl rollout status deployment/payment -n robot-shop
```

**Option B: Rollback payment deployment** (if issue started after deploy)
```bash
kubectl rollout undo deployment/payment -n robot-shop
```

**Option C: Drain and recreate MySQL pod** (use with caution — verify data persistence)
```bash
# Ensure MySQL has persistent volume before proceeding
kubectl get pvc -n robot-shop

# Restart MySQL pod (PVC data will persist)
kubectl delete pod -n robot-shop -l service=mysql
```

**Option D: Clear stuck RabbitMQ queues**
```bash
# Port-forward to RabbitMQ management
kubectl port-forward -n robot-shop svc/rabbitmq 15672:15672
# Navigate to http://localhost:15672 → Queues → Purge stuck queues
```

#### Escalation
- **Immediate escalation** to Engineering Lead + Payment team if payment is down > 5 minutes
- **Notify Customer Success** if external customers are reporting failures
- Create P1 incident — payment outages are revenue-critical

### 3.4 RobotShopPodCrashLoop

**Alert Expression:**
```promql
kube_pod_container_status_waiting_reason{
  namespace="robot-shop",
  reason="CrashLoopBackOff"
} == 1
```

**Firing Condition:** Any pod in `robot-shop` namespace is in CrashLoopBackOff state  
**Severity:** Critical

#### Symptoms
- Pod STATUS shows `CrashLoopBackOff` in `kubectl get pods`
- Grafana shows pod restart count increasing rapidly
- Service may be degraded if multiple replicas are crashing

#### Diagnosis Steps

**Step 1: Identify the crashing pod**
```bash
# List all pods with their restart counts
kubectl get pods -n robot-shop

# Filter only problematic pods
kubectl get pods -n robot-shop | grep -E "CrashLoopBackOff|Error|OOMKilled"
```

**Step 2: Describe the pod for events and reasons**
```bash
# Replace <pod-name> with actual pod name
kubectl describe pod <pod-name> -n robot-shop

# Key things to look for in Events section:
# - OOMKilled → Out of memory, increase memory limits
# - ImagePullBackOff → Image registry issue
# - Liveness probe failed → App not responding to health check
# - Exit code 1 → Application crash (check logs)
# - Exit code 137 → OOMKilled (kernel terminated)
```

**Step 3: Check pod logs** (previous container if current won't start)
```bash
# Logs of the currently failing container
kubectl logs <pod-name> -n robot-shop

# Logs of the PREVIOUS container (before restart) — critical for crash diagnosis
kubectl logs <pod-name> -n robot-shop --previous

# If multi-container pod, specify container
kubectl logs <pod-name> -n robot-shop -c <container-name> --previous
```

**Step 4: Check for OOMKilled**
```bash
# Check if OOM is the reason
kubectl describe pod <pod-name> -n robot-shop | grep -A 5 "OOM\|Killed\|Exit Code"

# Check node memory pressure
kubectl describe node <node-name> | grep -A 10 "Conditions"

# Check pod memory usage
kubectl top pod <pod-name> -n robot-shop
```

**Step 5: Check image pull issues**
```bash
# If ImagePullBackOff, check the image name and tag
kubectl describe pod <pod-name> -n robot-shop | grep "Image:"

# Verify the image exists in Docker Hub / ECR
# Check imagePullSecrets are present
kubectl get secrets -n robot-shop | grep docker
```

#### Mitigation

**Option A: OOM — Increase memory limits**
```bash
kubectl set resources deployment <service-name> -n robot-shop \
  --limits=memory=512Mi \
  --requests=memory=256Mi
```

**Option B: Application crash — Rollback**
```bash
kubectl rollout undo deployment/<service-name> -n robot-shop
kubectl rollout status deployment/<service-name> -n robot-shop
```

**Option C: Image pull failure — Fix image reference**
```bash
# Edit deployment to fix image tag
kubectl edit deployment/<service-name> -n robot-shop
# Update spec.template.spec.containers[].image to valid tag
```

**Option D: Config/secret issue — Check environment variables**
```bash
kubectl describe deployment/<service-name> -n robot-shop | grep -A 20 "Environment"
kubectl get secrets -n robot-shop
```

#### Escalation
- Escalate to **Application Developer** if root cause is a code bug
- Escalate to **DevOps Lead** if infrastructure configuration is causing OOM across multiple services

### 3.5 ErrorBudgetBurning

**Alert Expression:**
```promql
# Critical (14× burn rate over 1h)
(
  sum(rate(http_requests_total{namespace="robot-shop", code=~"5.."}[1h]))
  / sum(rate(http_requests_total{namespace="robot-shop"}[1h]))
) / 0.005 > 14
```

**Firing Condition:** Error budget burn rate exceeds threshold  
**Severity:** Warning (6×) or Critical (14×)

#### Symptoms
- Alertmanager firing `ErrorBudgetBurning` or `RobotShopWebErrorBudgetCritical`
- Grafana SLO dashboard shows burn rate exceeding threshold
- Error budget widget showing rapid consumption

#### Diagnosis Steps

**Step 1: Check the burn rate dashboard**  
Navigate to: `http://grafana.monitoring.svc/d/robot-shop-slo`  
- Look at "Error Budget Remaining" gauge
- Look at "Burn Rate (1h)" and "Burn Rate (6h)" panels
- Identify which services are contributing to burn

**Step 2: Identify the time of onset**
```bash
# In Grafana, adjust the time range to when alert fired
# Look for the inflection point in the error rate graph
# Compare with deployment timeline in Grafana's annotations
```

**Step 3: Correlate with recent deployments**
```bash
# Check recent deployments
kubectl rollout history deployment -n robot-shop

# Check what changed recently
kubectl get events -n robot-shop --sort-by='.lastTimestamp' | grep -i "deploy\|scale\|update"
```

**Step 4: Identify error patterns by service**
```bash
# Break down error rate by service
kubectl logs -n robot-shop -l app=robot-shop --tail=500 | grep -E "5[0-9]{2}|ERROR" | sort | uniq -c | sort -rn
```

**Step 5: Review Jaeger traces** for abnormal spans  
Navigate to: `http://jaeger.monitoring.svc/search`  
- Filter by `Error: true`
- Sort by duration (longest first)

#### Mitigation

- If correlated with a recent deployment → **trigger rollback** (see 3.1 Option A)
- If external dependency is failing → **implement circuit breaker / retry logic**
- If traffic spike → **scale up affected services** (see 3.2 Option A)
- Notify stakeholders per [Error Budget Policy](../slo/error-budget-policy.md) thresholds

#### Escalation
- At **14× burn rate**: Page on-call engineer AND Engineering Lead immediately
- At **6× burn rate**: Notify SRE team, monitor closely

## 4. Common kubectl Commands

### 4.1 Pod Management

```bash
# List all pods in robot-shop namespace
kubectl get pods -n robot-shop

# List pods with extra info (node, IP)
kubectl get pods -n robot-shop -o wide

# List pods with restart counts
kubectl get pods -n robot-shop | awk 'NR==1 || $4>0'

# Watch pods in real-time
kubectl get pods -n robot-shop -w

# Describe a pod (events, resource usage, image details)
kubectl describe pod <pod-name> -n robot-shop

# Delete a pod (will be recreated by ReplicaSet)
kubectl delete pod <pod-name> -n robot-shop
```

### 4.2 Logs

```bash
# View last 100 lines of logs
kubectl logs <pod-name> -n robot-shop --tail=100

# Stream logs in real-time
kubectl logs <pod-name> -n robot-shop -f

# View logs from previous (crashed) container
kubectl logs <pod-name> -n robot-shop --previous

# View logs from all pods with a label
kubectl logs -n robot-shop -l service=web --tail=100

# View logs with timestamps
kubectl logs <pod-name> -n robot-shop --timestamps=true

# View logs since a time period
kubectl logs <pod-name> -n robot-shop --since=1h
```

### 4.3 Resource Usage (Top)

```bash
# Pod resource usage
kubectl top pods -n robot-shop

# Pod resource usage, sorted by CPU
kubectl top pods -n robot-shop --sort-by=cpu

# Node resource usage
kubectl top nodes

# Resource usage for a specific pod
kubectl top pod <pod-name> -n robot-shop
```

### 4.4 Deployments & Rollouts

```bash
# List deployments
kubectl get deployments -n robot-shop

# Check rollout status
kubectl rollout status deployment/<name> -n robot-shop

# View rollout history
kubectl rollout history deployment/<name> -n robot-shop

# Rollback to previous version
kubectl rollout undo deployment/<name> -n robot-shop

# Rollback to specific revision
kubectl rollout undo deployment/<name> -n robot-shop --to-revision=2

# Scale a deployment
kubectl scale deployment <name> -n robot-shop --replicas=3

# Restart all pods in a deployment (rolling restart)
kubectl rollout restart deployment/<name> -n robot-shop
```

### 4.5 Services & Networking

```bash
# List services and their endpoints
kubectl get services -n robot-shop

# Check service endpoints (verifies pods are linked)
kubectl get endpoints -n robot-shop

# Describe a service
kubectl describe service <name> -n robot-shop

# Port-forward for debugging
kubectl port-forward svc/<service-name> -n robot-shop 8080:80
```

### 4.6 Exec Into Pods

```bash
# Open a shell in a pod
kubectl exec -it <pod-name> -n robot-shop -- /bin/sh

# Run a single command
kubectl exec -n robot-shop <pod-name> -- curl -s http://catalogue/catalogue

# Test internal DNS resolution
kubectl exec -n robot-shop <pod-name> -- nslookup mysql
```

## 6. Incident Severity Levels

| Priority | Criteria | Response Time | Resolution Target | Examples |
|----------|----------|--------------|-------------------|---------|
| **P1 — Critical** | Complete outage, all users affected, revenue impact | 5 minutes acknowledge, 15 min first action | 1 hour | Payment service down, site completely unreachable |
| **P2 — High** | Major feature broken, > 25% users affected | 15 minutes acknowledge, 30 min first action | 4 hours | Cart service down, checkout failing for some users |
| **P3 — Medium** | Minor feature degraded, < 25% users affected | 1 hour acknowledge, 2 hours first action | 24 hours | Slow catalogue page, non-critical search errors |
| **P4 — Low** | Cosmetic issue, no user impact, tech debt | Next business day | 1 week | Alert noise, non-critical logging gaps |
